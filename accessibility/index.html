Accessibility

Built to help your app meet WCAG 2.2 AA

Skribly UI aims at WCAG 2.2 Level AA in everything it ships. This page says how, what the tests check, and what stays with the app that uses it.

The target, and what it is notLink to the section The target, and what it is not

Information: No claim of conformance

Conformance belongs to whole pages, not to parts. A library cannot make an app conformant on its own, and Skribly UI has not been audited or certified. It removes the common failures from the parts it supplies, and the app still owns its content, its words, its page structure and its own CSS.

Every component is designed against the AA criteria of WCAG 2.2, built on React Aria so keyboard, focus and screen reader behaviour follow the ARIA Authoring Practices, and documented with its own accessibility notes on its page.

What the tests checkLink to the section What the tests check

  • axe on every demo

    211 demos run through axe-core in the light, dark and high contrast themes: 633 runs on every npm test.

  • Contrast of the token pairs

    Text and tint pairs, control borders and the focus ring are measured in each theme against 4.5:1 and 3:1, or 7:1 and 4.5:1 in high contrast.

  • Every component is shown

    A test fails when an exported component has no demo, so nothing ships without being run through axe.

  • Behaviour per component

    Each component has Testing Library tests for its keyboard paths, accessible names, states and live messages.

  • This site in a real browser

    Before each release every page of this site is opened in Chromium at 320 and 1280 pixels wide and run through axe with layout, so target size, colour contrast in all three themes, links in text and scroll boxes are measured too. A page that scrolls sideways or is not found fails the build.

The unit tests run in jsdom, which has no layout. axe’s own contrast rule is off there, which is why the token pairs are checked from their values, and why the built site is checked again in a browser. Some things no automated test can see:

  • what a real screen reader says, and in which order;
  • whether the focus ring is visible against what is behind it;
  • layout at 400% zoom and on a 320px screen;
  • the words and the content your app puts in the components.

Those are checked by hand during review, and your app should check them too.

Screen readers and live messagesLink to the section Screen readers and live messages

Every component has a name, a role and a state. Names come from props, never from the library, so they are in the app’s language. Status words such as “Error” are read before the message, so the tone never rests on colour and icon.

Messages that appear later are read through live regions: polite for success and information, which waits for the screen reader to finish, and assertive for errors that stop the reader. LiveRegion and announce() do the same for an app’s own messages. The messages pattern says which component to use.

Reduced motionLink to the section Reduced motion

Motion is short and never needed to understand a change. With prefers-reduced-motion: reduce, or the a11y-reduce-motion class from the reader settings, the duration tokens drop to almost zero, pulses stop, theme changes switch at once and scrolling jumps. Spinners keep turning slowly, because a still spinner would say the work has stopped.

Forced coloursLink to the section Forced colours

Windows high contrast replaces every colour with a few system colours. Components keep their shape there: badges and tiles have transparent borders that become visible, the current item gets an underline or a Highlight bar, selected options use Highlight, and skeletons get an outline. Colour swatches, such as on the token tables, keep their real colours.

The high contrast theme is a separate thing: a theme of the library for readers who want strong contrast with the Skribly look.

Zoom, reflow and text spacingLink to the section Zoom, reflow and text spacing

  • Text sizes are in rem, so the browser text size setting scales every component.
  • At 400% zoom, a 1280px window is 320px wide. Components wrap, stack and truncate with the full text kept for screen readers, and nothing scrolls sideways except data tables and code, which scroll inside their own box.
  • Fields use 16px text below 640px, so phones do not zoom in when a field takes focus.
  • Text containers grow with extra line, word and letter spacing instead of clipping it.

Target sizeLink to the section Target size

Pointer targets are at least 24 by 24 pixels, the AA minimum of WCAG 2.2. Controls are 36px tall by default; the compact density makes them 30px, still above the minimum. Small close buttons get a 24px hit area even where the icon is smaller, and the steppers of the reader settings are 44px.

How to test your appLink to the section How to test your app

  1. 1Keyboard onlyPut the mouse away. Reach every control with Tab, use it, and see the focus ring all the way.
  2. 2A screen readerVoiceOver on macOS and iOS, NVDA on Windows, TalkBack on Android. Listen to names, states and messages.
  3. 3Zoom and 320pxZoom to 200% and 400%, and use a 320px wide window. Nothing should be cut off or scroll sideways.
  4. 4Forced colours and motionEmulate forced-colors and prefers-reduced-motion in the browser developer tools.
  5. 5Automated checksRun axe in unit tests and in end-to-end tests of real pages, where it can measure contrast.
  6. 6Your own contentRead every label, error and empty state aloud. Does it say what happened and what to do?
An axe check in Vitesttsx
import axe from 'axe-core'
import { render } from '@testing-library/react'

it('has no axe violations', async () => {
  const { container } = render(<SettingsPage />)
  const results = await axe.run(container, { rules: { 'color-contrast': { enabled: false } } })
  expect(results.violations).toEqual([])
})
An axe check in Playwright, with contrastts
import AxeBuilder from '@axe-core/playwright'

test('settings page', async ({ page }) => {
  await page.goto('/settings')
  const results = await new AxeBuilder({ page }).withTags(['wcag2a', 'wcag2aa', 'wcag21aa', 'wcag22aa']).analyze()
  expect(results.violations).toEqual([])
})
